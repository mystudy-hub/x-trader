## 目的与读者

本文把规划 §9.1 的分步实施路线展开为可执行的工作分解、里程碑、关键路径、工作量粗估和风险登记表，供项目负责人排期、开发人员领取工作项、评审人核对阶段出口。阶段总览由 requirements.json 生成，工作分解的提前实现不改变正式出口。新增建议使用 PROP 编号、标注【评审补充】并保持“待确认”；文档纠错及已确认的维护方式记录在 10，不等同于功能实现或柜台验收通过。

## 1. 实施原则

来源：规划 §1.2、§9.1。

1. **依赖顺序链固定**：策略类别、执行数据与规则日历 → 共享订单、账本与风控 → 单品种简化 Bar 回测与快速研究通道 → 多品种、移仓与硬约束 → 仿真、恢复、唯一执行服务与看门狗 → 影子模式与最小手数实盘 → 扩大范围与精细撮合。后一阶段不得在前一阶段出口未满足时宣称完成。
2. **薄切片**：阶段 3 先以简化撮合得到第一条可对账的权益曲线并开始策略研究；恢复、存储与精细撮合能力在后续阶段补齐。薄切片降低的是撮合精度，不是账务正确性。
3. **小仓位不是故障测试的替代**：最小手数实盘是安全边际，A02—A04、A14、A23 等故障与恢复用例仍须在进入实盘前通过。
4. **账本与冻结先于资金结果验收**：智能平仓路由、逐单冻结和一套账本的两种盈亏视图必须在任何回测资金结果被采信之前完成（阶段 2 出口）。
5. **日志与指标从基础阶段建设**：结构化日志与关联字段（FR-OPS-02）自阶段 1 起启用，不推迟到实盘前补。
6. **修订优先级**：真实资金损失后果优先于回测收益失真，收益失真优先于研究效率。排期冲突时按此顺序取舍。
7. **未核验不作默认**：交易所、柜台、数据供应商的具体规则须保存来源、生效时间和验证用例；未核验条目登记缺口，不进入实盘默认配置（FR-SCOPE-04、FR-RULE-04）。

#### S5-01 / S5-02 CTP 网关与回报归一化实现记录（2026-09-24）

接续 2026-09-23 的纸面装配，补齐"不接柜台也能验证"的部分，并按 SimNow 候选环境把配置装配打通。**S5-01、S5-02 仍在实现中**：登录 / 查询 / 报单的柜台证据尚未取得（本机到 SimNow 前置的 TCP 连接超时，见"未取得的证据"），S5-03 终端采集、S5-05 实盘引擎、S5-06 看门狗、S5-07 生命周期联调、S5-11 故障注入套件、S5-12 月度仿真均未交付；本记录不宣称 S5 阶段出口通过。

- **`gateway/ctp_gateway.py`（S5-01）**：连接 → 终端认证（AppID/AuthCode，未配置时明确记录并用不含该步骤的握手）→ 登录 → 结算确认的显式状态机；任一步失败或被柜台拒绝都抛出 `CtpHandshakeError` 并保持发送门禁关闭。CTP 回调运行在 C++ 线程，只做字段读取 / 转换 / 标识关联与入队，绝不改状态、写库或阻塞（ADR-X2）；回调函数直接写进 SPI 类命名空间，避免多继承下基类默认实现优先，测试对覆盖生效有断言。控制代次在"取命令后"与"实际调用 `ReqOrderInsert` / `ReqOrderAction` 之前"两次复核（ADR-X1、FR-RISK-07），不一致返回明确 `NOT_SENT` 且不调用接口。会话内按柜台返回的 `MaxOrderRef` 递增分配 `OrderRef`，并把 `(FrontID, SessionID, OrderRef)` 三元组随本地发送结果持久化，重启后可从已落盘事实恢复归属。
- **未核验能力禁用而非猜测**：平仓标志因今昨仓制度而别，只有登记中标记为已核验的交易所才允许发送平仓（`CtpOffsetMapping.verified`）；开仓标志由 API 头文件唯一定义（`THOST_FTDC_OF_Open='0'`），因此不依赖柜台能力核验，未登记时计数留痕。市价单需要 `order_types.market_order` 已核验（GAP-S0-05 未关闭，默认禁用）。撤单必须带完整原会话三元组：只有交易所单号时明确拒发，不用当前会话号补全。
- **发送结果保守化**：只有本地返回 0 才记 `SENT_UNKNOWN`（本地受理不等于柜台受理，`LocalSendResult` 本身禁止 `CONFIRMED_REMOTE`）；非零返回码"能否证明未发送"取决于柜台实测语义，未核验前一律保守记 `SENT_UNKNOWN` 并保留预占，核验后可用配置收窄为 `NOT_SENT`。规划阶段（开平映射、价格步长、字段构造）的本地失败可证明"没有发送"，返回 `NOT_SENT` 而不是让执行服务记成"可能已发出"。
- **`gateway/feedback_normalizer.py`（S5-02）**：报单 / 成交 / 纠错回报 → `OrderUpdate` / `Trade`。交易日只认柜台 `TradingDay`，缺失即失败；事件时刻优先用柜台日期 + 时间（交易所时区固定 UTC+8），与本地接收时刻明显不符（夜盘日期按交易日填写）时退回落接收时刻并计入 `timestamp_anomalies`，不拼出一个可能落在未来的时刻。平仓标志枚举无法表达的柜台标志（强平 / 强减 / 本地强平）明确失败进死信；撤单被拒等当前 `OrderUpdate` 表达不了的状态记入审计缺口并返回 `None`，不静默丢弃。成交去重键作用域为 `(account, exchange, trading_day, TradeID)`，其唯一性假设来自 API 声明并在 07 证据表登记为待联调核验；无法唯一归属的回报不编造标识：成交保留 `order_identity=None` 交内核待关联队列，报单回报没有标识可表达则记缺口。

- **字段长度校验**：柜台结构体是定长 `char` 数组，超长会在绑定层抛 `TypeError`（实测 `UserProductInfo` 超过 10 字符即失败）。`CtpSettings` 现在按头文件长度（BrokerID 10 / UserID 15 / InvestorID 12 / Password 40 / ProductInfo 10 / AuthCode 16 / AppID 32）在本地校验并给出可读错误。

## 9. 变更管理

1. **新增约束的入口**：任何新的业务约束一律先写成 07 文档中的验收案例（编号、场景、通过条件、证据类型），再决定是否修改设计文档正文。没有验收案例的约束不排入开发。
2. **范围扩展**：每增加交易所、品种、历史研究区间、账户、订单类型、保证金模式、策略类别或数据源，须补充规则来源、适配验证及回归案例，并更新 A25 适用清单；既有样例通过不能自动证明新增范围正确（来源：规划 §9.3 末条）。
3. **文档版本与 run_manifest 的关系**：清单至少锁定原规划 §5.5 的实际输入，可附文档基线、需求版本等审计元数据。审计元数据不替代数据、代码、规则、配置、依赖与日历的锁定；不得因文档修订覆盖已有实验或宣称其结果已改变。实际输入变化仍生成新实验标识。
4. **规则来源修订**：规则库中的修订保留旧版本并声明替代关系（FR-RULE-03）；受影响的实验生成新实验标识，不覆盖旧结果。
5. **【评审补充】项的处理**：按 PROP 编号同步 00、02、03、04、06、07、08、09；确认后在 10 记录范围及理由，保留既有 FR 编号并补齐正式验收与阶段。未确认议题不进入正式阶段出口。
6. **派生表维护**：需求、R 关联、状态、适用范围、分阶段交付及验收关系只在 requirements.json 维护，执行 `python scripts/check_docs.py --write` 生成，再用 `--check` 检查；业务正文人工维护。
