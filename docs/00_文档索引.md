## 追溯链

```text
规划原文 §x.y
   │
   ▼
01 原始需求 R-nn
   │
   ▼
02 需求拆解 FR-<域>-nn / NFR-nn ──► 07 验收案例 A01–A29、A25-01..07
   │                                   ▲
   ▼                                   │
04 架构 / 05 业务规则 ──► 06 开发计划 S0–S7 工作项 ──► 08 上线门槛
```

- 每条需求写明 `来源：规划 §x.y` 与验收编号。
- 每个验收案例在 02 的反向矩阵中至少对应一条需求。
- 每个开发阶段列出涉及的需求编号与出口验收编号。
- 代码提交与实验清单 `run_manifest.json` 引用需求编号和验收编号，形成从规划到运行结果的完整链。

## 术语与标记约定

- **【评审补充】**：来自 2026-09-13 评估、尚未写入规划的建议。状态一律为"待确认"，不得作为已决定的需求或设计执行。
- **须核验**：规划中标注需要交易所公告、期货公司说明或柜台联调证据的项。未核验前不得作为实盘默认值，登记在 09 的缺口表。
- **P0 / P1 / P2**：对应阶段与适用范围的必需项 / 非出口阻塞的优化项 / 按策略类别或能力启用；同一需求的基础部分与精细部分分别标注。
- **交付范围**：M3 是单品种 Bar 工程闭环，M4 是多品种研究交付，M6 是影子与最小手数实盘校准；“首版研究能力”不表示一次交付 S0—S6 的全部运行能力。
- **S0–S7**：开发阶段编号，与规划 §9.1 的阶段 0 到阶段 7 一一对应。
- **证据类型**：实时观测 / 历史回放 / 故障注入 / 柜台实测，四类分别标记，回放与注入不折抵实时运行时长。

## 维护规则

1. 来源规划保留原始内容与 SHA-256，作为追溯历史；不再直接改写。当前已确认约束以本轮基线及 10 中明确的变更记录为准。无已确认变更覆盖的部分继续遵守原规划；未决建议不得覆盖它。
2. 新的业务约束先写清 07 的验收场景、通过条件与证据类型，再更新需求清单及 02，最后同步 04/05 和受影响的 03/06/08/09。仅修正措辞、恢复遗漏或对齐引用时，也在 10 说明依据。
3. 需求编号、R 关联、来源锚点、状态、适用范围、分阶段交付与验收关系维护在 `docs/requirements.json`。01 的 R 表、02 的需求元信息及追溯/阶段表、03 的优先级表、06 的阶段总览与 07 的验收关联表由它生成；正文业务说明仍人工维护。
4. 修改清单后执行 `python scripts/check_docs.py --write`，提交前执行 `python scripts/check_docs.py --check`。校验同时检查原始验收、阶段任务、上线条件、脚本职责与 SQL 基线；有意改变这些内容时须先记录已确认的变更并更新校验依据。
5. 每份文档记录版本与日期；跨文档引用优先使用需求编号、案例编号、章节及锚点。实验清单可附文档基线和需求版本作为审计元数据，不能代替对数据、代码、规则、配置等实际输入的锁定。
6. 【评审补充】采纳或否决时，以 PROP 编号同步修改相关文档和 10。已有 FR 编号保持稳定；正式化时补充验收、来源和阶段，不因状态变化重新编号或复用旧编号。
7. 范围扩展按原规划 §9.3 补充规则来源、适配验证及回归案例，更新 A25 适用清单。规格夹具标记为未执行，不能作为柜台实测或已通过验收的证据。
8. 根目录 README 维护项目入口；流程文档继续使用 00–10 主线编号。参考资料按主题放入 references/，新的评审记录按 `YYYY-MM-DD_主题.md` 放入 reviews/；冻结来源放入 sources/。迁移文件须同步相对链接、需求清单和规格夹具中的来源路径，并在 10 登记。
