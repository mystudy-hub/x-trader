## 二、阻塞项（S4 出口前必须修复）

### B1. 连续序列复权用了新合约自身的隔夜跳空，不是合约间价差；纯价差切换产生假信号

`qh_trader/data/continuous.py:121`：`gap = bar.open - yesterday_new_contract_bar.close`。这是新合约自己的隔夜变动，与旧合约无关；合约间价差应为 `yesterday_new_contract_bar.close - prev_bar.close`。`RATIO` 分支（第 131 行）同样把新合约开盘除以旧合约收盘。

复现（新旧合约各自价格恒定 3000 / 3100，只有 100 点价差，持仓量第 6 日交叉）：

| 输出 | 现实现 | 应有 |
| :--- | :--- | :--- |
| `adjusted_close` 序列 | 3000 ×6 → **3100** ×4 | 3000 ×10 |
| `single_day_return` | 全 0（正确） | 全 0 |
| `RollAwareTrendStrategy`（2/4 均线）在平价上的交易 | 第 9 日 BUY OPEN @3100，净亏 1.50 | 无交易 |

策略消费的是 `adjusted_close`（`multi_product.py:210-212`），不是 `single_day_return`；A10 测试（`test_s4_acceptance_a10.py:100`）只断言后者，所以没有暴露。在真实 S4 数据上，切换日的序列跳空与合约自身当日涨跌严重脱节：AP 2026-04-09 跳空 −1392 点而合约自身 +1.67%，jd 2025-04-14 跳空 +715 点而自身 −0.62%，cu 2024-10-18 跳空 +720 点。8 个品种 44 次切换全部带入了这种假动量。

这正是 FR-CON-03 / A10 "新旧合约各自价格不变而存在价差时，切换不产生虚假动量"要否定的情形。已验证一行修复（`gap = yesterday_new_contract_bar.close - prev_bar.close`）使上例序列变为 3000…3007 连续，且不改变 `single_day_return`。`RATIO` 同法改为 `yesterday_new.close / prev_bar.close`。第 124 行的兜底（新合约无昨日 Bar 时用原始跳空）须按 FR-CON-03 "缺少调整参考价时明确标记"输出降级记录，而不是静默采用。补 `adjusted_close` 连续性的成对样本测试，并重跑 S4 报告。

### B2. 第二腿失败后移仓永久卡在 `LEG_2_SUBMITTED`，账户空仓却无任何报告

复现（第二腿目标合约被交易所限额规则拒绝开仓）：第一腿平仓成交，第二腿本地拒绝，`RollTask` 停在 `LEG_2_SUBMITTED`（leg1 1 手、leg2 0 手、`failure_reason=None`），策略 `_roll_task` 永不清空，`on_bar` 每根 Bar 提前返回（`multi_product.py:215`），此后该品种不再交易；`roll_records` 为空，报告与清单里"移仓次数"不计这次失败，最终持仓 0 手而策略以为仍持有。

原因有两层：策略从不调用 `RollManager.on_order_rejected_or_cancelled`；引擎的本地拒绝路径（`base_engine.py:515` `_reject_locally`、第 444/596 行 `NOT_SENT` 分支）不向策略发送任何回报，只有网关回报才触发 `strat.on_order`。FR-CON-06 "未完成移仓时报告实际剩余持仓和风险暴露"、FR-VAL-03 报告须含"未完成移仓"均未满足。现有 `test_roll_manager_failure_paused` 只测 `RollManager` 单元路径。

修复：引擎对本地拒绝合成 `OrderUpdate(status=REJECTED)` 送策略（或增加 `on_reject` 回调）；策略在拒绝 / 撤单 / 过期时调用 `on_order_rejected_or_cancelled`，`PAUSED` 任务按配置重试或上报；报告增加"未完成移仓"表（任务、已成交腿、剩余暴露、原因）。

### B3. 任何本地拒单都会让该品种策略永久停摆

复现（资金不足以开 1 手）：第 3 日意图被风控拒绝，`_inflight = {rb2501}` 直到回测结束，10 个交易日只创建了 1 张委托。根因与 B2 相同：`_inflight` 按合约登记、只在收到终态回报时清除（`multi_product.py:234-243`），而本地拒绝没有回报。S4 报告"未成交 / 错过执行 0 笔"是在这一前提下得到的。修复同 B2；另外 `_inflight` 应按 `client_order_id` 而非合约登记，否则父单拆成两个子单时第一个子单终态就会提前放行。

### B4. S4 数据摄取覆盖了 S3 工程样本，来源与时段标签混杂

`scripts/fetch_s4_test_products.py:129` 对包括 rb 在内的全部品种 `save_bars`，把 rb2410 自 2024-06-03 起的 89 根日线从 tushare 来源换成 sina 来源：`session_id` 由 `day` 变为 `day_continuous`（`schemas.py:341` 默认值），`includes_auction` 由 True 变 False，质量标记变 `TURNOVER_UNAVAILABLE`，1 根 Bar 收盘价不同（2024-09-25：3128 → 3136），37 根成交量不同；而执行参考价数据集仍是 `session_id=day`。

后果：当前发布快照下工程样本独立预期不可比（回放脚本已报"不可比"）；启用执行参考价时 89 根 Bar 的开盘候选按 A25-07 降级，成交 23 → 15 笔。07 §4.4 要求工程样本与研究数据集分开管理，FR-VAL-07 要求数据补录生成新标识而非覆盖当前引用。旧快照 `4379bc81…` 仍可用，所以证据链没断，但当前指针已指向混合样本。修复：S4 摄取排除已发布的工程样本合约，或写入独立数据集命名空间；统一 `session_id` 词汇表（`day` / `day_continuous` 二选一，并与日历、执行参考价一致）；重新发布后更新 `tests/fixtures/backtest_expectations.json` 的快照固定值。

### B5. 有夜盘品种的日线 Open 被标成 09:00 日盘开盘，未经来源核验

S4 日线全部按 `open_time = 09:00`、`session_id = day_continuous`、`includes_auction = False` 落库（`schemas.py:364-390`）。`config/data_coverage.yaml` 对同一数据集写的是"日线 Open 不区分夜盘与日盘"且"待核验"。对 rb / MA / i / m / au / cu 这些有夜盘的品种，交易所口径的日线 Open 通常是前一自然日 21:00 夜盘首笔，引擎却按"T 日 09:00 日盘开盘价"用它撮合 `NEXT_BAR_OPEN`。这正是 A21 "含夜盘日线 Open 不冒充日盘 Open"和 FR-EXEC-02 "只有数据源定义证实日线 Open 正是所选时段的价格时才允许使用"所禁止的；引擎的日历一致性检查因 09:00 落在日盘时段而放行。

修复：先核验 sina 日线 Open 的时段归属并写入 `data_coverage.yaml`；有夜盘品种的日线 `open_time` 应指向日历中 `night_continuous` 的开始（前一自然日 21:00，交易日仍为 T），或不生成执行参考价并让开盘候选按 A25-07 降级；无夜盘品种（AP、jd）可保持 09:00。修复后 S4 报告须重跑。

## 三、主要缺陷（出口前应修复）

### M1. 主力切换 `effective_from` 记为确认日收盘时刻，而非 T+1 首个可交易时段

`dominant_contract.py:151` `switch_time = top_bar.bar_end`，`effective_from == decision_time`。FR-CON-02："若使用 T 日完整日盘数据，默认不早于 T+1 交易日首个可交易时段生效"。策略在 T 日 15:00 查询即得到新主力并发起移仓，成交落在 T+1 开盘，所以没有成交级前视；但映射记录本身与规格不符，连续序列在确认日 T 也已用新合约 Bar 拼接。应把 `effective_from` 记为 T+1 首个可交易时段（由日历给出），并在清单中保存 `decision_time` 与 `effective_from` 的差。

### M2. 长假识别按"相邻交易日自然日间隔 > 3"推断，与公告不符

`session_templates.py:106-108`。复现：2024-12-31 → 2025-01-02 间隔 2 天，模板为 12-31 晚生成夜盘，而交易所公告元旦前一工作日无夜盘；2025-12-31 因间隔 5 天反而正确。任何间隔 ≤ 3 天的法定假日（元旦、单日清明 / 端午等）都会错生成夜盘。A05 / A25-05 明文"不按自然日加减"。日历版本 `s4-2024v1` 的交易日本身也来自 sina 观测（`observed_sina_trading_days`），不是公告归档。需要节假日公告版本表驱动夜盘取消与节后竞价，间隔启发式只能作为标记"待核验"的降级。

### M3. S4 运行清单不可追溯，报告缺规格要求的项

`scripts/run_multi_product.py` 自建清单：无数据快照 ID、无 Git 提交、无依赖锁哈希、无订单 / 成交 / 账本规范哈希、日历只有模板哈希无版本号；未复用 S3 的 `build_manifest`。报告缺"未完成移仓"、逐次移仓明细（两腿合约、价格、时刻、暴露天数）、日 / 夜盘拆分、实际滑点对假设滑点（FR-CON-07、FR-VAL-03）。重跑结果虽与提交一致，但换一份数据快照无法察觉。

### M4. 移仓手续费重算而非取账本事实；窗口过滤可混入无关成交

`multi_product.py:562-573` 用 `spec.commission_per_lot × 数量` 重算，与其 docstring "从账本成交事实里取"及 FR-CON-07 "手续费逐笔计算"不符；且按时间窗口筛同合约成交，同窗内的信号交易会被计入移仓手续费。应按两腿的 `client_order_id`（含子单）从 `result.closed_trades` / 账本 COMMISSION 条目取值。

### M5. 递延平仓意图跨日后仍以原 `CLOSE_TODAY` 发出，由内核静默改桶

`positions.py` 新增的 `effective_offset(trade, client_order_id)` 在成交 offset 与预占 offset 不一致时以预占为准。触发场景正是 S4 引入的"15:00 意图持有到 21:00 送出"：意图在 T 日按今仓规划为 `CLOSE_TODAY`，21:00 已属交易日 T+1，持仓已转昨仓，真实 SHFE 柜台会拒绝该平今单，回测却成交并改记平昨。FR-ORD-01 "回测与实盘同一实现"被绕过。递延意图应在实际送出时刻由 `SmartRouter` 重新规划开平标志；内核改桶逻辑至少要写入对账标记并有领域测试（当前没有）。

### M6. S4-04 长假钩子未接入多品种回测，日历无节假日标记

`research/`、`engine/`、`scripts/` 中没有任何 `HolidayRiskHook` / `holiday_dates` 引用；`RiskManager` 默认 `holiday_hook=None`。FR-RISK-06 要求"回测中同样执行，使历史收益反映节前处理的成本"，06 记录却把 S4-04 列为完成。需要日历提供长假标记（源于公告），装配层按品种配置钩子，并在报告列出节前减仓成本。

### M7. 无时段门时日线回测静默全数过期

复现：同一策略与数据，去掉 `session_gate` 后 10 天 0 成交、9 张委托 EXPIRED、0 拒单、0 错过执行。原因是 15:00 意图立即送到网关被接受，随后日切按 GFD 过期。这是 S3 引擎在日线粒度下的陷阱，S4 靠"装配层总是带日历"绕过。引擎应在 Bar 粒度不细于时段而又无时段门时明确失败，或把 GFD 过期绑定到时段门的交易日边界。

### M8. A10 测试深度不足，06 记录"A10 通过"言过其实

`test_s4_acceptance_a10.py` 只断言 `single_day_return`、`OPEN_FIRST` 顺利路径；`test_s4_multi_product.py` 的移仓测试用逐日上涨价格，B1 无症状。缺：成对样本（本评审探针通过，但无测试固化）、纯价差样本经账本无盈利、两腿部分成交、资金不足、第二腿拒绝后的剩余仓位报告。`test_a10_cross_day_order_and_spread_invariants` 有两个未使用变量（ruff F841）。

### M9. 合约目录与解析绕过 `ContractResolver`

`load_product_dataset` 直接从数据集键构造 `InstrumentId`，`config/contract_catalog_s4_2024v1.json` 的 `listed_on` 取首个观测日、`available_at` 早于 `listed_on`；05 §8.2 / A29 要求保留原始柜台代码并结合交易日与目录版本解析（郑商所 `MA501` 已被规范化为 `MA2501`，原码只存在别名里）。当前样本区间无跨十年歧义，风险低，但应经 `ContractResolver` 走一遍并记录解析依据。
