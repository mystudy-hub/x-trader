# S5 进程模型、IPC、回调汇入与时钟同步设计评审（S5-13 / ADR-X1 · X2 · X3）

- 评审对象：04 系统架构设计 §12.2 待决项 ADR-X1（进程模型与 IPC）、ADR-X2（CTP 回调线程汇入执行序列）、ADR-X3（本机时钟同步与偏差监控）
- 对应需求：FR-REC-06（进程模型与 IPC、CTP 回调汇入，已转正式需求，见 10 的 2026-09-21 决定）、FR-CAL-13（本机时钟同步与偏差监控，仍待确认）
- 对应计划项：06 开发计划 S5-13、风险 R9（进程模型 / IPC / 时钟未设计导致 S5 返工）
- 关联已决项：ADR-02（独立执行服务为唯一交易出口，单实例，持久化 `controller_id` / `control_epoch`）、ADR-03（单一账户执行序列串行更新，回调只入队）、ADR-04（交易事件与元数据用 SQLite WAL+FULL，本地磁盘，不用网络共享文件）
- 评审日期：2026-09-21
- 目的：在 S5 实现前定下这三项，避免执行服务、看门狗、代次校验、恢复对账的实现骨架返工。本文给出方案对比与推荐，决策权保留给项目负责人；已于 2026-09-21 确认并落地：ADR-X1/X2/X3 转入 04 §12.1，FR-REC-06 转正、FR-CAL-13 保持待确认，记录见 10 文档变更记录。

## 结论先行

| 决策项 | 推荐方案 | 一句话理由 |
| :--- | :--- | :--- |
| ADR-X1 进程模型与 IPC | **命令面走 SQLite `command_queue`（候选 3）；事件订阅面复用现有 `SQLiteJournal`的只读游标视图，不新建事件表；不引入 ZMQ / 命名管道** | 首版单机单账户低频 CTA 对延迟不敏感；命令必须可审计、带代次、崩溃可恢复，这些正是 SQLite 事务的强项；订单事件已有 `journal.py` 作为唯一事实源，不再另立一张表 |
| ADR-X2 回调汇入 | **专用执行线程 + 两个线程安全队列（候选 1），交易队列优先于行情队列** | CTP 回调在 C++ 线程，"只转换、入队"最易推理；asyncio + `call_soon_threadsafe` 与 CTP 封装 GIL 释放行为耦合，首版不值得这个复杂度 |
| ADR-X3 时钟同步 | **OS 层 NTP 同步 + 开盘前同步状态检查 + 单调时钟测耗时（候选 1），偏差只记录并在超阈值时进入保守门禁** | 不自建时钟同步协议；墙钟用于时段边界、单调时钟用于耗时/超时，二者不混用；接收时间减事件时间只作传输+处理时延指标 |

三项相互支撑：SQLite 命令表天然满足 A23 接管序列的"命令带代次、崩溃后可恢复、乱序/重复可去重"；专用执行线程消费该命令表与 CTP 回调队列，处理结果写入既有 `SQLiteJournal`（不新建事件表）；时钟方案为命令表的时间戳与开盘检查提供口径。

> 本文为实现方自评经一轮独立评审后的修订版。独立评审指出 5 处会在 S5 实现时返工的技术漏洞（多进程写锁、事件源重复、接管授权序列缺失、回调线程背压、Windows NTP 可信度），本版逐条修订，修订点在各节以【评审修订】标出。三项推荐方向未变，落地约束按评审收紧。

## 一、ADR-X1 进程模型与 IPC

### 问题

策略进程、独立执行服务、看门狗、人工控制之间如何传递意图、事件、心跳与控制命令；`control_epoch` 如何随消息传递并在接收端校验（04 §5 逻辑消息流已定，物理机制未定）。

### 候选对比

| 维度 | 候选 1 命名管道 + 长度前缀 | 候选 2 ZMQ REQ/REP + PUB/SUB | 候选 3 SQLite 命令表 +（复用）Journal 事件视图（推荐） |
| :--- | :--- | :--- | :--- |
| 外部依赖 | 无（Windows 原生） | 引入 `pyzmq` 原生依赖 | 无（复用 `live/trading.db` 与既有 `SQLiteJournal`） |
| 延迟 | 亚毫秒 | 亚毫秒 | 取决于轮询周期（建议 50–200ms，低频 CTA 足够） |
| 可审计 | 需自建落盘 | 需自建落盘 | **天然持久化，命令即审计记录** |
| 携带代次 | 需自定义协议字段 | 需自定义协议字段 | **命令行内含 `control_epoch` 列，接收端 SQL 校验** |
| 崩溃恢复 | 管道断开消息丢失，需重放层 | 队列高水位丢消息，需重放层 | **命令表持久，重启后从游标续读；事件重放复用 Journal `replay_from`** |
| 乱序/重复/去重 | 需自建序号与幂等层 | 需自建序号与幂等层 | **主键 + 状态列 + 游标，去重与幂等直接落在表约束上** |
| 与 ADR-04 一致性 | 另起一套 IPC 语义 | 另起一套 IPC 语义 | **同一事务模型，命令与订单事件（Journal）同事务提交** |
| 事件事实源 | 另起一套，与 Journal 重复 | 另起一套，与 Journal 重复 | **不新建事件表，订阅面 = Journal 只读游标视图，单一事实源** |
| 多进程写锁 | 不涉及（各进程独占管道端） | 不涉及 | **需显式处理：多进程 INSERT 竞争全库写锁（见落地约束）** |
| 首版复杂度 | 中（重连、序列化、多客户端） | 中高（消息丢失、高水位、原生依赖跨平台） | **低（但写锁与授权序列须显式设计）** |
| 不适用场景 | — | — | 若未来升级到亚秒高频多账户，轮询延迟与全库写锁成为瓶颈 |

### 推荐：候选 3（SQLite `command_queue` + 复用 Journal 事件视图）

理由：

1. **命令面的核心诉求是可审计 + 带代次 + 崩溃可恢复**，不是低延迟。首版低频 CTA 明确对延迟不敏感（04 §12.2 ADR-X1 取舍要点），SQLite 事务恰好把这三个诉求一次满足。
2. **与 ADR-04 同一事务模型**：执行服务在同一 SQLite 事务里"读命令 → 风控 → 持久化订单意图（写 Journal）→ 更新命令游标"，天然满足 ADR-02 的"本地事务提交后再网络发送"（FR-RISK-07）。命令处理与订单落库不会出现半提交。
3. **A23 接管序列直接落在表结构上**：`control_epoch` 是命令行的列；接管时旧代次命令被 SQL 谓词直接拒绝，崩溃重启后从处理游标续读，无需另建重放层。
4. **零新增依赖**，不引入 ZMQ 的跨平台原生构建与高水位丢消息问题。

### 【评审修订】事件事实源：复用 Journal，不新建 `execution_events` 表

自评初版曾提议新建 `execution_events` 表供订阅。独立评审指出这与 `infrastructure/journal.py` 现有的 `SQLiteJournal`（`append` / `replay_from` / `snapshot`，S2 恢复协议与 S5-10 事件重放均建立其上）形成两套事实源，订单事件要写两处。**修订为**：

- 执行服务处理结果只写 `SQLiteJournal`（唯一事实源），不新建事件表。
- 策略/看门狗的"事件订阅"= 对 Journal 按 `seq` 游标的**只读**读取（一致读快照，S1-08 已保证读事务一致性）；各订阅方维护自己的读游标。
- 只有 `command_queue` 是本评审新增的表；`execution_events` 一词在下文与图示中一律指"Journal 的只读游标视图"，不是独立表。

### 【评审修订】多进程写锁与 INSERT 失败处置

自评初版用"单写者"一句带过，实际上策略、看门狗、人工入口都要 `INSERT command_queue`，即多进程写同一库。SQLite 写锁全库串行，执行服务在"读命令 → 风控 → 写 Journal → 推游标"的写事务持锁期间，其他进程 `INSERT` 会得到 `SQLITE_BUSY`（这正是 04 §12.2 候选 3 提示"本地文件需单独评估"处）。修订为明确的锁与失败契约：

- **WAL 下读写并发**：`live/trading.db` 已按 ADR-04 用 WAL，读者（订阅方）不阻塞写者；写者之间（多个 INSERT + 执行服务事务）仍全库串行。
- **`busy_timeout`**：所有连接（含各命令生产者）设 `busy_timeout`（建议 5000ms），INSERT 遇写锁在超时内自动重试，不立即失败。
- **执行服务写事务尽量短**：单条命令的"风控 → 写 Journal → 推游标"作为一笔短事务提交，缩短持锁窗口；不在持锁期间做网络发送（发送在事务提交后）。
- **生产者 INSERT 幂等**：命令携带客户端生成的 `command_id`（UUID），重试 INSERT 用 `INSERT OR IGNORE`，`busy_timeout` 内重试与进程崩溃补投都只落一行。
- **INSERT 最终失败的意图处置**：超 `busy_timeout` 仍失败时，生产者不得静默丢弃：策略把该意图标记为"未送达"并按其策略语义处置（撤回或下一 Bar 重试），人工入口向操作者报错要求重试，看门狗接管申请失败按 FR-RISK-08 保守处理（不接管、告警）。失败计入指标（FR-OPS-03）。

### 【评审修订】接管授权序列（A23 核心，不能只画一根箭头）

自评初版只给出"旧代次命令 `WHERE control_epoch = :current` 拒绝"，但看门狗的接管申请本身不持有当前代次，按同一谓词会被误拒。补全授权序列：

1. **签发新代次的权力不在看门狗**：看门狗只能向 `command_queue` `INSERT` 一条 `kind=TAKEOVER_REQUEST` 的申请（携带申请者身份、原因、当前观测到的 `control_epoch`），它本身不提升代次、不获得交易权（FR-RISK-08：心跳超时不授予交易权）。
2. **接管申请的受理是独立仲裁步骤**，不走"旧代次即拒"的普通命令谓词：由**新的执行服务实例启动流程**（人工发起或按预案）来受理。**【二次评审修订】受理序列对齐 07 A23 通过条件——隔离 → 提升代次 → 对账 → 放行**：新实例读到 `TAKEOVER_REQUEST` 后执行"旧出口隔离 → 原子提升 `control_epoch`（旧 + 1，且不回退，FR-RISK-07）并持久化 → 柜台查询对账（FR-REC-04）→ 对账通过后才放行新代次发单"。全过程由账户执行序列串行推进；隔离和柜台查询在 SQLite 写事务外，代次 / 阶段 / 审计在各自短事务内原子提交，不能持有数据库写锁等待网络。
3. **代次先于对账提升是关键**：07 A23 通过条件为"先停发旧命令、持久化新代次并对账，再允许新控制者操作"。若按"先对账再提升"，对账窗口内旧代次仍是当前代次，F14 场景（旧控制者网络恢复重发）会在窗口内漏过；先提升代次后，对账期间旧控制者补发的命令已被普通谓词（`REJECTED_STALE`）拒绝，堵住该窗口。
4. **旧出口隔离先于代次提升**：提升代次前必须确认旧执行连接已断开或无法再发单（旧实例检测到自己非当前控制者后停止发送，ADR-02 后果条款）；隔离未完成不提升代次（FR-RISK-08：旧出口无法隔离时不另建交易连接）。
5. **对账通过是放行发单的门槛**：代次提升后、放行新代次发单前，用柜台查询合并本地游标状态（FR-REC-04），确认无在途/未知订单遗留；对账未通过不发新单。接管审计（申请、隔离结果、新旧代次、对账结果）全部落 Journal，供 A23 验收核对。

### 落地约束（写入 04 §12.1 与 S5 实现）

- **一张新表**：`command_queue`（策略意图、看门狗申请、人工命令；列含 `command_id` UUID 主键、`control_epoch`、`controller_id`、`kind`、`payload`、`submitted_at`、`status`、`processed_seq`）；事件订阅复用 `SQLiteJournal`（见上"事件事实源"修订）。均在 `live/trading.db`（ADR-04）。
- **单一写者写 Journal**：只有执行服务写 `SQLiteJournal` 并推进 `command_queue.status`；命令生产者只 `INSERT command_queue`（受 `busy_timeout` + `INSERT OR IGNORE` 约束，见写锁修订），只读 Journal。
- **代次校验在接收端**：执行服务取普通命令后先核对 `control_epoch`，旧代次命令标记 `REJECTED_STALE` 并写审计，不执行（FR-RISK-07）；接管申请走上文独立仲裁序列，不套用此谓词。发送前再复核一次（ADR-02 后果条款）。
- **轮询而非阻塞（【二次评审】主循环形态）**：执行服务以 `trade_event_queue.get(timeout=轮询周期)` 等待交易回报，每批最多处理固定条数并受单调时钟预算约束；每批结束都轮询一次 `command_queue`，不只在超时时轮询，否则连续回报会使撤单和人工命令一直得不到处理。交易队列为空时至多消费一项行情，不无限排空行情队列。轮询周期为 50–200ms，写入 run/live manifest，作为容量与延迟指标记录（FR-OPS-05）。
- **心跳不入 `trading.db`（【二次评审修订】）**：同一库只有一把写锁，若心跳表与 `command_queue` 同库，策略与执行服务每秒 UPDATE 心跳会与命令事务、其他进程的 INSERT 抢锁，正是写锁修订要避免的事。心跳不需事务与审计，放到**独立文件**：单独的 `heartbeat.db` 或每角色一个时间戳文件（`role`、`instance_id`、`beat_monotonic`、`beat_wall`、`updated_at`），与交易库写锁完全隔离。策略→看门狗心跳、以及看门狗监测执行服务自身存活都走该通道；执行服务定期更新自己的心跳，看门狗读取判断执行服务是否失联。心跳超时本身不授予交易权（FR-RISK-08）。
- **明确非目标**：本方案不承担网络共享文件的多进程协调（ADR-04 已排除），仅本机多进程；跨机存活告警仍由独立于交易主机的外部心跳承担（04 §5，规划 §4.5.5）。

### 需要的验证（S5-11 故障注入 / A23）

- 命令丢失（进程崩在 INSERT 后、处理前）→ 重启从游标续读，命令不丢不重复执行。
- 命令重复（同 `command_id` 重投）→ 主键 + `INSERT OR IGNORE` 幂等，只执行一次。
- 多进程并发 INSERT 遇写锁 → `busy_timeout` 内重试成功；超时失败时意图按上文处置并计指标，不静默丢弃。
- 旧代次命令（接管后旧控制者补发）→ `REJECTED_STALE`，不发送到柜台。
- 接管序列（A23，对齐 07 顺序）→ 看门狗申请不自授权；新实例执行隔离→提升代次→对账→放行，全序列可核对；隔离未完成不提升代次，对账未通过不放行发单。
- 接管对账窗口内旧控制者网络恢复重发（F14）→ 代次已先提升，重发命令被 `REJECTED_STALE` 拒绝，不漏到柜台。
- 进程崩溃后消息恢复 → 重启对账游标与柜台查询合并（FR-REC-04）。

## 二、ADR-X2 CTP 回调线程汇入执行序列

### 问题

CTP 封装的回调运行在 C++ 线程；如何把回调事件安全交给单一账户执行序列（ADR-03 回调只入队），同时保证行情队列不阻塞交易队列。

### 候选对比

| 维度 | 候选 1 专用执行线程 + 线程安全队列（推荐） | 候选 2 asyncio 事件循环 + `call_soon_threadsafe` |
| :--- | :--- | :--- |
| 回调职责 | 只做字段校验、转换、`put`（不改状态） | 只做转换、`call_soon_threadsafe`（不改状态） |
| 交易/行情隔离 | 两个独立队列，交易队列优先消费 | 需在单循环内自建优先级，行情回调可能阻塞循环 |
| 与 CTP GIL 行为耦合 | 低（标准 `queue.Queue`，线程语义清晰） | 高（需确认封装 GIL 释放，回调阻塞会拖住整个循环） |
| 与虚拟时钟/回测复用 | 回测用 `VirtualClock` 驱动，实盘用线程队列，调度抽象分离但语义一致 | 号称可统一调度抽象，但回测本就不需要 asyncio |
| 异常安全 | 回调内 try/except，转换失败入死信，不丢队列 | 回调抛异常可能逃逸到循环，需额外保护 |
| 首版复杂度 | 低，易推理 | 中高 |

### 推荐：候选 1（专用执行线程 + 双队列）

理由：

1. **CTP 回调在 C++ 线程，"只转换、入队"是最小且最易验证的契约**。`queue.Queue`（线程安全）语义清晰，回调线程只 `put`，执行线程串行 `get` 并按 04 §6.1 区分命令分支与事实分支。
2. **交易队列与行情队列物理分离**，交易队列优先消费（04 §6.2 明确"交易事件优先处理；订单或成交无法可靠保存时立即禁止新增风险并告警"）。行情洪峰不会饿死订单回报处理。交易队列无界、行情队列有界，回调侧均使用 `put_nowait`；行情满时按质量门禁记录丢弃，交易回报不因消费慢而阻塞或丢弃（见落地约束背压修订）。
3. **asyncio + `call_soon_threadsafe` 的唯一卖点是"统一调度抽象"**，但回测通道用 `VirtualClock` 驱动、根本不需要 asyncio；实盘引入单循环反而把行情回调、定时器、IPC 轮询耦合在一起,一个阻塞点拖垮全部。首版不值得。
4. 与 ADR-X1 协同：执行线程同时消费 CTP 回调队列与 SQLite 命令表（轮询），两个来源在同一执行线程内串行汇入账户执行序列（ADR-03）。

### 落地约束

- **两条入站队列**：`trade_event_queue`（订单回报、成交回报、查询应答、错误）与 `market_data_queue`（行情）。执行线程先清交易队列再处理行情（04 §6.2 优先级）。
- **回调只入队、绝不改状态**（ADR-03）：字段校验/转换失败的事件进死信记录并告警，不静默丢弃，不阻塞队列。
- **【评审修订】回调线程永不阻塞——交易队列无界 + 高水位告警**：自评初版写"交易队列宁可阻塞不丢"，独立评审指出这会阻塞 CTP 回调线程：回调线程被 `put` 阻塞后，CTP 内部分发线程随之停住，直接后果是心跳丢失、被柜台判定断线并触发重连——比丢一条回报更糟。**修订为**：交易队列用无界 `queue.Queue()`（回调线程 `put_nowait` 永不阻塞、永不丢），并设高水位阈值，队列深度越过阈值即告警（消费端跟不上是需要人工介入的严重信号），高水位不通过丢弃或阻塞回调来"泄压"。真正的耐久性保证在执行线程侧：事件一旦 `get` 出来，先写 `SQLiteJournal`（ADR-04 的 FULL 同步）再处理，订单/成交的"不丢"由持久化承担，而不是靠阻塞入站队列。队列深度、高水位越界次数计入指标（FR-OPS-03）。
- **行情队列可有界丢弃**：`market_data_queue` 可设上限与丢弃计数（低频下不触发，但需登记）；行情丢弃适用数据质量容忍度，交易队列不适用（04 §6.2）。
- **消费端持续无法保存的处置**：若执行线程侧 Journal 写入持续失败（磁盘满等），按 04 §6.2"订单或成交无法可靠保存时立即禁止新增风险并告警"，进入只平不开的保守门禁，而非在入站侧阻塞。
- **去重在执行序列内**：乱序/重复/迟到成交（A02）的去重按 S2 已实现的按作用域成交去重与状态投影处理，回调层不做业务去重。
- **回投**：执行线程处理后将订单/成交/状态写 `SQLiteJournal`（唯一事实源，见 ADR-X1 事件事实源修订），供策略与看门狗按游标只读订阅。

### 需要的验证（S5-11 / A02）

- 回调期间抛异常 → 事件不丢，进死信 + 告警，执行线程继续。
- 交易队列高水位（模拟慢消费）→ 回调线程仍 `put_nowait` 不阻塞、不丢；高水位告警触发；CTP 心跳不受影响。
- 执行线程侧 Journal 写入持续失败 → 进入只平不开保守门禁并告警，不回压 CTP 回调线程。
- A02 乱序 / 重复 / 迟到回报 → 执行序列内去重，账本一致。

## 三、ADR-X3 本机时钟同步与偏差监控

### 问题

规划 §6.3 用毫秒延迟建模，A25-04 区分 08:59:00 与 08:59:01 到达，但未定义本机时钟与交易所/柜台时间的对齐方式（FR-CAL-13 待确认）。

### 候选对比

| 维度 | 候选 1 OS NTP 同步 + 开盘前检查 + 单调时钟测耗时（推荐） | 候选 2 不主动同步，仅记录偏差、超阈值进保守门禁 |
| :--- | :--- | :--- |
| 时钟对齐 | 依赖 OS/NTP 服务，开盘前核对同步状态 | 不对齐，只观测 |
| 耗时/超时测量 | 单调时钟（`time.monotonic`），不受墙钟跳变影响 | 同样需单调时钟 |
| 偏差指标 | 记录 NTP 提供的可信偏差 + 事件时间与本地接收时间差（后者含传输+处理时延，不等同纯时钟偏差） | 只记录接收-事件差 |
| 时段边界判定 | 由日历 + 状态回报共同判断，墙钟辅助 | 同 |
| 开盘检查 | 同步状态与偏差进 08 §4.1 开盘检查 | 偏差进开盘检查，但无同步保证 |
| 风险 | 依赖运维配置 NTP | 无同步时边界与事件关联误差不可控 |

### 推荐：候选 1（OS NTP + 开盘前检查 + 单调时钟）

理由：

1. **不自建时钟同步协议**。交易主机的墙钟由 OS/NTP 负责,系统只在开盘前核对同步状态并记录可信偏差指标,超阈值进入保守门禁。自研同步协议既无必要也难验证。
2. **墙钟与单调时钟严格分工**（04 §12.2 ADR-X3 取舍要点）：墙钟用于时段边界与事件关联,单调时钟（`time.monotonic`）用于耗时和超时测量,二者不混用。墙钟跳变不影响超时判定。
3. **接收时间减交易所事件时间只作"传输+处理时延"指标,不认作纯时钟偏差**（FR-CAL-13 描述明确)。两个指标分开记录,避免把网络延迟误判为时钟偏差。
4. **时段边界不单靠墙钟**：仍由日历 + 柜台状态回报（InstrumentStatus）共同判断（04 §5）,墙钟偏差只影响事件关联质量,不直接决定开平市。

### 【评审修订】Windows 的 OS NTP 不能默认可信

自评初版把"OS NTP"当作既有可信基线。独立评审指出：非域 Windows 机器的 `w32time` 默认同步周期长、精度粗，偏差可能达数秒到数分钟；若不核验，A25-04 那种秒级到达边界（08:59:00 vs 08:59:01）就没有依据。**修订为**：NTP 源配置是部署前提而非假设，开盘前检查必须实读同步状态而非假定已同步。

### 落地约束

- **两类时钟分离**：所有耗时/超时/心跳间隔用 `time.monotonic`；所有事件时间戳、时段边界、审计时间用墙钟（UTC 存储,展示按交易所时区),与 `core/objects.py::RecordMeta` 已有的 UTC 事件/接收/可见/导入时刻一致。
- **【评审修订】NTP 源为部署前提**：交易主机必须显式配置可信 NTP 源（列入 08 部署前提与运维手册），不依赖 Windows 默认 `w32time` 行为；域外机器须手动配置 NTP 服务器并缩短同步周期。未配置可信 NTP 源视为部署未就绪。
- **【评审修订】开盘前实读同步状态**：`scripts/preopen_check.py`（S5-07）在 Windows 上读 `w32tm /query /status`（`w32tm /query /source`、`/stripchart` 视需要）的实际偏差、上次同步时刻、同步源，而不是假定已同步；偏差超阈值或上次同步时间过旧（阈值待定,登记为 FR-CAL-13 待确认项）时开盘检查失败或进入保守门禁。检查结果（原始输出 + 解析值）留痕。
- **两个偏差指标分列**：`clock_offset`（NTP/`w32tm` 报告的可信偏差）与 `event_receive_latency`（本地接收时间 − 事件时间,含传输+处理）分开记录进指标（FR-OPS-03),不相互替代。
- **回放不伪造同步证据**：Bar/Tick 回放用 `VirtualClock`,合成的零偏差不得当作实盘同步证据(04 §12.2 ADR-X3 验证条款)。
- **阈值待定**：具体同步方式、偏差阈值、证据质量规则属 PROP-07 待确认范围,本评审只定框架,阈值在 S5 联调用实测数据确定。

### 需要的验证

- 开盘前同步状态与偏差指标进入 08 §4.1 开盘检查并留痕（含 `w32tm /query /status` 原始输出与解析值）。
- 未配置可信 NTP 源或上次同步时间过旧 → 开盘检查判定部署未就绪/进入保守门禁，不放行正常开仓。
- 墙钟人为跳变时,超时/心跳判定（单调时钟）不受影响。
- 回放场景 `clock_offset` 明确标记为虚拟,不计入实盘同步证据。

## 四、三项决策的协同关系

```
策略进程 ──INSERT 意图(带 epoch)──> command_queue(SQLite) ──轮询──┐
人工控制 ──INSERT 命令(带 epoch)──> command_queue(SQLite) ──轮询──┤
看门狗   ──INSERT 接管申请────────> command_queue(SQLite) ──轮询──┤
                                                                 v
CTP C++ 回调线程 ─put_nowait─> trade_event_queue(无界)──┐   [执行线程 = 账户执行序列]
                 ─put_nowait─> market_data_queue(有界) ─┤   代次校验 → 风控 → 写 Journal → 发送
                                                        └get(交易优先)─> 处理
                                                                 │
                                              ┌──写入 SQLiteJournal（唯一事实源）──┘
                                              v
                       策略/看门狗按 seq 游标只读订阅 Journal（非独立事件表）

心跳：策略→看门狗、执行服务→看门狗 走独立 heartbeat.db 或时间戳文件（不入 trading.db）
时钟：命令/事件时间戳 = 墙钟(UTC)；轮询周期/超时/心跳 = 单调时钟
```

- ADR-X1 命令表为 ADR-X2 执行线程提供命令来源之一（另一来源是 CTP 回调队列）,二者在同一执行线程内串行汇入；事件回投复用既有 `SQLiteJournal`，不新建事件表。
- ADR-X3 为命令表时间戳、开盘检查、事件关联提供时钟口径。
- 三者共同支撑 A23（接管序列）、A02（回报去重）、A04（恢复对账）、A26（开盘检查）。
