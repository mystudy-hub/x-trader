## 目的与读者

## 1. 架构目标与设计原则

| 原则 | 含义 | 来源 / 需求 |
| :--- | :--- | :--- |
| 共享交易内核 | 订单状态机、平仓路由、持仓与资金账本、规则查询、风控、移仓逻辑在回测、影子、模拟盘与实盘中只有一套实现。`BaseEngine` 只负责组织运行，禁止在回测和实盘中各自维护资金或持仓算法。 | 规划 §3.4；FR-ORD-*、FR-LED-*；NFR-01 |
| Port / Adapter | 领域逻辑只依赖端口协议；历史数据、虚拟时钟、SimulatedGateway、内存 Journal 与 CTP 适配器、实时时钟、SQLite Journal 作为可替换实现由入口装配。 | 规划 §3.4；NFR-03 |
| 单向依赖 | 运行时的行情、意图和回报流向不等于 Python 的导入方向；依赖按 §3 的表约束，由依赖检查验证禁止边与循环。 | 规划 §3.4 模块依赖约束；NFR-03 |
| 事件驱动与单一执行序列 | 同一账户的订单、持仓、账本与风控状态由一个执行序列串行更新；回调只转换、入队。 | 规划 §3.4；FR-RISK-01 |
| 可复现 | 同一环境、输入和随机种子下重跑得到相同订单、成交和账本；实验快照锁定数据、代码、规则、配置与依赖。 | 规划 §3.2、§5.5；NFR-01、FR-VAL-07 |
| 保守门禁 | 未知状态先对账、禁止盲目重发；结算未完成、差异未解释、数据质量超限时禁止新增风险，但回报处理、对账与监控继续运行。 | 规划 §4.1.4、§4.2、§4.6；FR-REC-*、FR-RISK-* |
| 可见性约束 | 策略只能查询 `available_at <= 当前策略时钟` 的数据，禁止直接读取数据湖获取未来信息。 | 规划 §3.4；FR-DATA-03 |
| 性能不改语义 | 性能优化不得改变舍入、事件顺序或交易语义。 | 规划 §3.4 回测模式的端口适配；NFR-02 |

首版范围（FR-SCOPE-01）：Windows、单账户、普通期货合约、多品种低频 CTA、Bar 事件驱动回测与 CLI 报告。本文的实盘拓扑、Tick 录制与排队估算按规划 §9.1 阶段逐步启用，架构在首版即为其预留位置，但不要求首版实现。

## 2. 总体结构

来源：规划 §3.4。

```text
CLI / scripts / 后续 GUI
          |
Strategy API: on_bar / on_tick / on_order / on_trade
              target_position(product) / buy / sell / short / cover / 查询当时可见数据
          |
共享领域内核
  OrderManager + SmartRouter + Positions + Ledger
  RuleBook + RiskController + RollManager + RecoveryCoordinator + DailyLifecycleManager
          |
  端口：Execution / MarketData / Clock / Journal / RuleStore / MappingStore / AccountQuery
          |
          +-- 回测适配器：历史数据、虚拟时钟、SimulatedGateway、内存 Journal
          +-- 实盘运行：独立执行服务、CTP 适配器、实时时钟、账户查询与回报
          +-- 持久化适配器：交易事件库、规则库、行情文件、实验清单
```

各层职责：

| 层 | 职责 | 不做的事 |
| :--- | :--- | :--- |
| CLI / scripts | 唯一装配入口：选择运行模式（回测 / 回放 / 影子 / 模拟 / 实盘）、注入具体适配器、启动引擎或服务。 | 不实现业务算法；其他层不反向导入。 |
| Strategy API | 策略以品种为单位表达目标仓位或下单意图，也可显式指定实际合约；通过协议查询当时可见数据。 | 不导入具体引擎；不读数据湖；不直接调用交易 API。 |
| 共享领域内核 | 订单管理、平仓路由、持仓冻结、账本、规则查询、风控、移仓、恢复协调、每日生命周期。 | 不读取数据湖、不调用 CTP、不感知运行模式。 |
| 端口 | 领域内核与外部世界之间的协议边界。 | 端口只定义协议，不含实现。 |
| 适配器 | 端口的具体实现：回测、实盘、持久化。 | 网关归一化回报，不直接改持仓或账本。 |

### 2.1 品种级策略接口与合约解析

来源：规划 §3.4；FR-ORD-08。

- 策略层以品种为单位表达目标仓位或下单意图；共享内核按当时可见的主力映射和账户移仓状态，把品种意图解析为具体实际合约的开平子订单。策略也可显式指定实际合约（套利、移仓测试）。
- 持仓查询同时返回品种净头寸和实际合约明细，明细含今昨仓。多策略共用账户时，同品种反向意图按策略归属分别记账、按账户净额路由；是否允许锁仓由账户配置决定，并在阶段 2 之前确定。
- 解析结果、所用映射版本和归属策略随订单意图一起持久化。

### 2.2 回测模式的端口适配

来源：规划 §3.4。

- 交易事件库端口在回测模式使用内存适配器，运行结束时导出规范事件供快照与对账；SQLite 事务日志只服务模拟盘与实盘。
- 回测使用虚拟时钟；行情可见、订单到达、成交和回报到达分别建事件。同时间事件的优先级与排序规则固定并纳入运行清单。实盘回放保留实际接收顺序。

## 3. 分层与模块依赖约束

来源：规划 §3.4 模块依赖约束；NFR-03。

| 模块 | 允许的项目内依赖 | 边界 |
| :--- | :--- | :--- |
| `core/` | 本层无环依赖 | 纯类型、事件、常量与端口协议，不导入业务域或适配器。 |
| `domain/`、`strategy/` | `core/` 及各自模块内的无环依赖 | 领域层不读取数据湖或调用 CTP；策略通过协议查询数据、提交意图，不导入具体引擎。 |
| `data/`、`gateway/`、`infrastructure/`、`monitor/` | `core/` 及各自模块内的无环依赖 | 实现端口，通过注入的协议获取所需服务；网关归一化回报，不直接改持仓或账本。 |
| `engine/` | `core/`、`domain/` | 组织账户执行序列、生命周期和端口调用，接收注入的策略与适配器；独立执行服务放在本层。 |
| `scripts/` / CLI | 上述模块 | 唯一装配入口，选择运行模式和具体实现；其他层不反向导入入口。 |

补充约束：

- 领域组件可通过明确的值对象和无环调用协作，不要求每次内部调用都新增端口。共享规则、映射、时钟与持久化通过端口注入。
- 依赖检查（`tests/architecture/`）同时验证禁止边和循环依赖，不能仅以"模块可导入"作为通过条件。阶段 2 出口要求该检查通过（规划 §9.1）。
- 防止 `risk`、`smart_router` 与对象定义互相导入：对象定义放 `core/objects.py`，风控与路由都只依赖 `core/`。
- `engine/` 不导入 `data/`、`gateway/`、`infrastructure/`、`monitor/` 的具体类；这些实现由 `scripts/` 装配后以端口类型注入。

## 4. 端口定义

来源：规划 §3.4。以下用简要 Protocol 伪代码描述主要操作；具体签名在 `core/ports.py` 中实现时确定，但职责与边界不得改变。所有端口的时间参数使用带时区的时间戳；所有查询类端口返回值附带来源、版本或可见时间信息，供策略可见性校验与快照记录。

### 4.1 ExecutionPort

职责：接收共享内核已经通过风控并持久化的最终子订单与撤单请求，返回明确的本地调用语义，并把柜台回报归一化为统一领域事件送回账户执行序列。

```python
class ExecutionPort(Protocol):
    def submit(self, order: OrderIntent, epoch: ControlEpoch) -> LocalSendResult: ...
    def cancel(self, ref: OrderIdentity, epoch: ControlEpoch) -> LocalSendResult: ...
    def capabilities(self) -> CapabilityProfile: ...
    # 回报不经返回值传递，而是以 OrderEvent / TradeEvent 入队到账户执行序列
```

- `LocalSendResult` 必须能区分"明确未发送"与"已受理但远端未知"（FR-ORD-06）；不能把所有异常或非零返回统一归为未发送。
- 发送前复核控制代次（FR-RISK-07）：适配器在真正调用网络接口前再次核对 `control_epoch`。
- 回测适配器：`gateway/simulated_gateway.py`，按 05 文档 §17—§20 的撮合与延迟规则生成回报事件。
- 实盘适配器：`gateway/ctp_gateway.py` + `gateway/feedback_normalizer.py`，覆盖本地调用返回、`OnRspOrderInsert`、`OnErrRtnOrderInsert`、`OnRtnOrder`、`OnRtnTrade` 及撤单错误回报。
- 影子模式：真实行情 + `SimulatedGateway`；小额并行时同一意图分别进入模拟撮合与唯一真实执行服务（FR-VAL-05）。

### 4.2 MarketDataPort

职责：向策略与撮合提供满足可见性约束的行情；实时模式下负责订阅与录制队列的对接。

```python
class MarketDataPort(Protocol):
    def subscribe(self, instruments: Sequence[InstrumentId]) -> None: ...
    def bars(self, instrument: InstrumentId, interval: str, until: Timestamp) -> Sequence[Bar]: ...
    def execution_reference(self, instrument: InstrumentId, session_id: str,
                            reference_time: Timestamp, price_type: str) -> ExecutionReference | None: ...
    def latest_tick(self, instrument: InstrumentId) -> Tick | None: ...
    def instrument_status(self, instrument: InstrumentId) -> InstrumentStatus | None: ...
```

- 任何返回记录必须满足 `available_at <= 当前策略时钟`（FR-DATA-03）；缺少所选执行时点的价格时返回空并由调用方明确失败，不插值、不借用其他时段价格（FR-EXEC-03）。
- 回测适配器：`data/replay.py` 从版本化 Parquet 读取；实盘适配器：CTP 行情连接 + `data/recorder.py` 有界队列。

### 4.3 ClockPort

职责：提供当前时间与定时事件，使日历、延迟、查询超时、定时任务在回测与实盘下由同一接口驱动。

```python
class ClockPort(Protocol):
    def now(self) -> Timestamp: ...
    def schedule(self, at: Timestamp, event: TimerEvent) -> None: ...
```

- 回测 / 回放：虚拟时钟，定时事件即使没有新 Tick 也推进（FR-MATCH-07）；倍速只控制墙钟播放速度，不改变事件时间、可见时间和同时间事件顺序（FR-VAL-06）。
- 实盘：实时时钟。【评审补充】本机时钟与交易所时间的偏差监控见 ADR-X3，状态待确认。

### 4.4 JournalPort

职责：交易事件库的持久化协议——订单意图、发送状态、柜台标识映射、待关联成交、规范事件、逐单预占、控制记录、处理游标、账户快照。

```python
class JournalPort(Protocol):
    def append(self, tx: JournalTransaction) -> JournalSeq: ...   # 同一事务提交去重、账本、预占、游标
    def snapshot(self, seq: JournalSeq) -> None: ...
    def replay_from(self, seq: JournalSeq) -> Iterator[CanonicalEvent]: ...
    def load_control_record(self) -> ControlRecord: ...
```

- 事件去重、账本更新、预占变更和处理游标在同一事务提交（FR-REC-03）；持久化失败时不得继续发送增加风险的订单（FR-DATA-07）。
- 回测适配器：`infrastructure/memory_journal.py`；实盘 / 模拟盘：`infrastructure/journal.py`（SQLite `live/trading.db`）。

### 4.5 RuleStorePort

职责：按查询时点、账户配置、实际合约返回唯一适用的规则版本：合约参数、手续费、保证金、能力表、交易时段、账户资金使用规则。

```python
class RuleStorePort(Protocol):
    def contract_rule(self, instrument: InstrumentId, profile: AccountProfileId,
                      effective_at: Timestamp, known_at: Timestamp) -> ContractRule: ...
    def commission_rule(self, instrument: InstrumentId, profile: AccountProfileId, offset: Offset,
                        effective_at: Timestamp, known_at: Timestamp) -> CommissionRule: ...
    def margin_rule(...) -> MarginRule: ...
    def capability(self, exchange, product, broker_profile, ctp_version, at) -> Capability | Unknown: ...
    def sessions(self, instrument: InstrumentId, trading_day: Date) -> Sequence[Session]: ...
```

- `effective_at` 是要核算的业务生效时刻，`known_at` 是查询者允许获知规则的时刻；策略/事前风控的适配视图将 known_at 限制在当前策略时钟内。账务按实际生效规则计费，晚发布修订以新的差额更正事件入账，不重写过去的策略决策（FR-RULE-03）。
- 相同查询时点与账户下适用规则必须唯一；无法唯一确定时抛出明确错误，不猜测（FR-RULE-01）。
- SQLite 适配器：`infrastructure/rule_store.py` 读取 `meta/control.db` 并实现规则查询端口；数据库迁移由装配入口调用基础设施代码完成。
- `domain/rules.py` 消费注入的 RuleStorePort / 值对象，完成规则选择、计费和保证金领域逻辑，不直接读库；`data/calendar.py` 解析注入的日历规则数据。入口负责装配，保持 §3 的依赖边界。

### 4.6 MappingStorePort

职责：提供已发布版本的主力映射、连续因子与合约解析，供 `RollManager`、`continuous.py` 与策略消费。

```python
class MappingStorePort(Protocol):
    def dominant(self, product: ProductId, at: Timestamp) -> DominantMapping: ...   # 仅返回 effective_from <= at 且 available_at <= at 的版本
    def resolve(self, raw_symbol: str, as_of: Date, catalog_version: str) -> InstrumentId: ...
    def continuous_factors(self, product: ProductId, at: Timestamp) -> ContinuousFactors: ...
```

- `RollManager` 只通过本端口消费已发布版本，不自行扫描数据文件或重算主力（FR-CON-04）。
- `resolve` 必须结合记录所属交易日与当时有效的合约目录，缺日期或多候选时报错（FR-CON-01，A29）。

### 4.7 AccountQueryPort

职责：向恢复协调器与生命周期管理器提供资金、持仓、订单、成交查询，附查询批次、所属交易日、完成标志与流控信息。

```python
class AccountQueryPort(Protocol):
    def query_account(self, batch: QueryBatch) -> AccountRaw: ...
    def query_positions(self, batch: QueryBatch) -> PositionsRaw: ...
    def query_orders(self, batch: QueryBatch) -> OrdersRaw: ...
    def query_trades(self, batch: QueryBatch) -> TradesRaw: ...
    def rate_limit(self) -> QueryRateLimit: ...   # 间隔、最大在途数，按目标柜台核验配置
```

- 查询未完成不得当作完整快照；限流需退避（FR-ORD-02）。
- 半结算或跨交易日混合的查询保存为待核对原始快照，不发布为可交易快照（FR-CAL-12）。
- 回测：`SimulatedGateway` 提供一致快照；实盘：`ctp_gateway.py`。

## 5. 运行时拓扑

来源：规划 §3.4、§4.5.5、§4.6。

```text
                +-------------------+        心跳         +------------------+
                |   策略进程         | ------------------> |  看门狗进程        |
                |  Strategy + 共享  |                     |  monitor/watchdog |
                |  内核（只读账户视图）|                     +---------+--------+
                +---------+---------+                               |
                          | 意图（品种 / 实际合约）+ controller_id/epoch  | 申请接管 / 撤单 / 减仓命令
                          v                                          v
                +------------------------------------------------------------+
                |          独立执行服务  engine/execution_service.py           |
                |  唯一 CTP 交易连接（单实例）                                  |
                |  账户执行序列：控制权校验 -> 风控 -> 同一事务持久化 -> 发送      |
                |  RecoveryCoordinator / DailyLifecycleManager / RiskController |
                +------+--------------------+--------------------+-----------+
                       |                    |                    ^
                       v                    v                    | 人工命令（携带代次）
                 live/trading.db      CTP 交易前置          monitor/control.py
                 (SQLite, WAL, FULL)

                +-------------------+      有界队列       +-------------------+
                | CTP 行情连接       | -----------------> | data/recorder.py  |
                +-------------------+                     | 分段 -> 原子发布   |
                                                          +-------------------+
```

| 组件 | 持有的状态 | 通信方向 | 约束 |
| :--- | :--- | :--- | :--- |
| 策略进程 | 策略内部状态、当时可见的数据视图、账户只读视图 | 向执行服务提交意图；接收订单 / 成交事件；向看门狗发心跳 | 不直接登录交易接口；不读数据湖。 |
| 独立执行服务 | `controller_id` / `control_epoch`、订单意图与发送状态、预占、持仓、账本、风控计数、生命周期阶段、处理游标 | 接收策略 / 移仓 / 看门狗 / 人工命令；向 CTP 发送；向 Journal 写事务 | 单实例；唯一持有该账户 CTP 交易连接；所有交易操作按控制者与代次校验；本地事务提交后再网络发送（FR-RISK-07）。 |
| 看门狗进程 | 心跳超时配置、接管申请记录 | 检测策略心跳；超时后按配置告警等待人工或申请接管 | 心跳超时本身不授予交易权；旧交易出口无法隔离时不另建交易连接（FR-RISK-08）。 |
| 人工控制入口 | 无持久状态 | 通过执行服务提交暂停 / 撤单 / 减仓 / 查询 / 恢复 | 须由当前控制者执行或完成接管；经同一风控与记账路径并留审计（FR-RISK-09）。 |
| 行情录制队列 | 内存队列、未封闭分段、已持久化文件、已提交清单四级水位 | 行情连接 -> 有界队列 -> 分段文件 -> manifest | 与交易事件队列隔离，交易事件优先；积压或写入失败计数告警（FR-DATA-04）。 |
| 独立于交易主机的存活告警 | — | 接收主机心跳 | 同机看门狗不能覆盖主机断电或整机失联（规划 §4.5.5）。 |

运行环境约束（规划 §4.5.5、NFR-07）：禁止交易时段自动重启与睡眠；Windows 更新安排在维护窗口并做重启后检查；本地开发机不承担实盘运行；部署位置结合实测网络质量选择。

【评审补充】策略进程、执行服务、看门狗、人工控制之间的具体 IPC 机制规划未指定，见 ADR-X1，状态待确认。在决策前，以上"通信方向"只表达逻辑消息流。

## 6. 并发与执行序列模型

来源：规划 §3.4、§4.5。

### 6.1 单一账户执行序列

- 同一账户的订单、持仓、账本与风控状态由一个执行序列串行更新。CTP 回调（行情、订单回报、成交回报、查询应答、错误）只做字段校验、转换和入队，不直接修改状态。
- 交易命令分支：接收意图或控制命令 -> 核验控制者与代次 -> 适用的事前风控（规则、价格数量、自成交、资金、敞口、报撤额度）-> 同一事务记录意图与相应预占 -> 提交成功后发送或生效（最终复核代次）。暂停、撤单、减仓和恢复分别检查其适用条件，不为每种命令机械创建新的开仓预占。
- 事实事件分支：接收订单/成交回报 -> 字段与标识校验 -> 关联或保存待关联占位 -> 去重 -> 在同一事务更新订单事实、持仓、账本、逐单预占及游标 -> 提交后发布一致视图并评估风险。真实成交不因旧代次、已有熔断或当前资金不足而被丢弃；不能对已发生事实重新执行“是否准许该成交”的事前风控。
- 两条分支由同一账户执行序列串行处理。事实引起新的撤单/减仓意图时，该新命令再进入命令分支；回报入账本身不直接调用交易 API。
- 提交失败：不发布未提交视图，不发送增加风险的订单；回滚暂存变更或从最后已提交状态重建。无法可靠保存真实回报时立即禁止新增风险、保留待核对状态并告警；远端发送结果未知的请求继续保守预占，不能按“未发送”处理（FR-REC-03）。
- 控制权切换与发送使用同一执行序列，避免校验通过后被旧控制者继续发单。

### 6.2 队列与优先级

| 队列 | 生产者 | 消费者 | 容量与故障策略 |
| :--- | :--- | :--- | :--- |
| 交易事件队列 | CTP 交易回调、策略意图、看门狗 / 人工命令、定时器 | 同一账户执行序列，按 §6.1 区分命令与事实 | 优先处理；订单或成交无法可靠保存时立即禁止新增风险并告警，不能套用行情录制的数据质量容忍度。 |
| 行情录制队列 | CTP 行情回调 | `recorder.py` | 有界；积压指标；超过数据质量容忍度时禁止新增风险；不能阻塞交易事件队列。 |
| 分析 / Compaction 队列 | 盘中或盘后任务 | DuckDB / `compact_ticks.py` | 资源预算隔离，避免争用实盘资源。 |

### 6.3 回测与回放的事件调度

- 虚拟时钟驱动；行情可见、订单到达、成交、回报到达分别建事件，各自配置延迟（FR-MATCH-07）。
- 同时间事件的优先级与排序规则固定并写入运行清单；相同时刻的成交与撤单按固定、可测试的顺序处理。
- 实盘回放保留实际接收顺序，不重排。
- 固定输入在单步、原速、加速下应得到相同规范订单、成交、预占及账本结果（A28）。

【评审补充】CTP 回调线程如何汇入执行序列（专用线程 + 队列还是 asyncio 事件循环）规划未指定，见 ADR-X2。

## 7. 数据架构

### 7.1 三种存储的职责边界

来源：规划 §3.2、§5.3、§5.4；FR-DATA-06、FR-DATA-07。

| 存储 | 职责 | 边界 |
| :--- | :--- | :--- |
| Parquet（版本化） | 规范行情、结算、执行参考、主力映射等已发布数据集 | 按内容或版本不可变发布；不原地写入。 |
| DuckDB | 已发布 Parquet 的只读分析 | 从指定数据集 manifest 获取文件列表及版本，禁止通配符混读多版本；跨品种 / 基本面联表必须带合约键、交易日、实际时刻及 `available_at` 条件；记录查询耗时、峰值内存、临时磁盘并设资源预算。 |
| SQLite | 事务与元数据：`meta/control.db`、`live/trading.db` | 受控写入者、短事务、本地受支持磁盘；不用网络共享文件做多进程协调。 |

### 7.2 行情分段录制与原子发布

来源：规划 §5.1；FR-DATA-04、FR-DATA-05。首版历史 Bar 直接写入版本化 Parquet；接入实时行情后采用短周期完整文件与清单发布。标准 Feather / Arrow IPC 文件依赖完整文件结构，不承担可任意追加、断电后自动恢复的 WAL 承诺。

```text
原始行情 -> 独立有界队列 -> 按时间或大小封闭一个完整分段
                                     |
raw/{source}/{trading_day}/{segment_id}.arrow.tmp
                                     |
关闭写入器 -> 持久化文件 -> 校验结构、行数及哈希
                                     |
同文件系统原子重命名为 .arrow -> 登记已提交 manifest
                                     |
compact_ticks.py 读取已发布分段并生成新的规范版本
                                     |
canonical/tick/{exchange}/{instrument_id}/{trading_day}/{version}/part-*.parquet
```

要求：

- 时间窗、大小阈值、压缩和 Row Group 大小通过代表性样本测定；可合并同来源多个合约控制小文件数。分段周期只是配置项，不能直接推导最大数据损失时间。
- 临时文件对读者不可见；崩溃后隔离未完成文件。完整文件已重命名但清单未提交时，恢复程序校验后补登记；清单只引用已完成且校验通过的文件。
- 使用目标平台的持久化接口，测试进程崩溃、断电恢复及磁盘满；分别记录内存队列、未封闭文件、已持久化文件、已提交清单的水位，按实测定义 RPO。
- 每批行情保留本地采集序号、连接标识及来源序号（若有）；本地序号不能证明链路从未丢包，断线和来源缺口单独标记。
- Compaction 由已封闭分段和交易时段水位驱动，可盘中或盘后执行，不绑定 15:30；重复执行不重复纳入同一来源记录；排序、去重和修订规则版本化。
- 规范文件生成新版本后原子发布，保留原始分段及快照引用；按引用关系和保留策略回收旧文件，禁止覆盖仍被实验引用的内容。
- 更低 RPO 的追加日志（长度边界、序号、校验和、同步水位、残缺尾部恢复）后续按需引入，并经故障注入验证。订单与成交从一开始使用事务性交易事件库，不依赖行情分段。

### 7.3 规范目录分层

来源：规划 §5.2。规范目录按 `bar/1m`、`bar/5m`、`bar/1h`、`bar/1d`、`execution_reference`、`tick`、`settlement` 分层，再按实际合约、交易日或月份分区并保存版本。派生视图保留源数据及日历版本，不改变源记录的可见时间。文件路径使用安全编码后的标识。涨跌停控制优先使用对应交易日的实际价格边界。

### 7.4 数据集 Schema

来源：规划 §5.2；FR-DATA-01、FR-DATA-02。

通用标识与时间：

| 字段 | 类型及语义 |
| :--- | :--- |
| `instrument_id`、`symbol`、`exchange` | 稳定的实际合约标识、原始柜台代码、交易所；完整交割年月放在合约目录中，连续序列另有类型标识。 |
| `event_time` | 事件实际发生时间，统一存储为带 UTC 时区的时间戳，展示及交易日历计算使用 `Asia/Shanghai`。 |
| `receive_time` | 本地实际收到实时消息的时间；历史文件无此信息时为空，不能伪造为实测接收时间。 |
| `available_at` | 在回测中允许策略获知该记录的最早时间，来自历史发布时间或有明确标识的发布 / 传输延迟假设。 |
| `trading_day`、`session_id` | 结算交易日使用 DATE；时段标识用于跨夜盘、竞价、休市及特殊交易日处理。 |
| `source_id`、`source_seq`、`ingest_seq` | 来源及其序号（若提供）、本地采集序号；序号作用域及连接重置规则需要定义。 |
| `ingested_at`、`schema_version`、`quality_flags` | 本次导入时间、结构版本及质量标记；导入时间不等于历史可获知时间。 |

同一版本文件中不变的来源、Schema 等信息可放入文件元数据和 manifest，逻辑 Schema 必须完整可恢复。时间戳精度不能超过来源实际提供的精度。

业务数据集：

| 数据集 | 必需字段与处理规则 |
| :--- | :--- |
| Bar | `bar_start`、`bar_end`、`interval`、`open/high/low/close`、本周期 `volume` / `turnover`、期末 `open_interest`。明确区间边界、覆盖时段、Open 所属时刻、竞价归属及可见时间；未完成 Bar 不按最终 OHLC 发布。 |
| ExecutionReference（派生视图） | 实际合约、目标 `session_id`、`reference_time`、`price_type`、参考价格、源记录标识、来源版本与分辨率、可见时间及质量标记。仅从确实覆盖所选执行时点的原始数据生成，区分夜盘开盘、日盘开盘、下一 Bar 开盘及固定盘中时刻；成交量若来源未提供则为空，不借用整日成交量冒充该时刻可用量。 |
| Tick / L1 快照 | `last_price`、`bid_price_1/ask_price_1`、`bid_volume_1/ask_volume_1`、交易日累计成交量和成交额、持仓量、`pre_settlement_price`、实际 `upper_limit_price/lower_limit_price`、交易状态。更深盘口按来源能力扩展。 |
| Settlement | 实际合约、交易日、官方 `settlement_price`、前结算价、`published_at`、可见时间、临时 / 最终状态、修订版本及来源；结算修订作为新记录发布。 |
| Instruments | 原始代码及别名、完整交割年月、上市 / 到期及最后交易日、乘数、最小价格变动、账户最晚平仓限制、常规夜盘能力及其生效版本；关联短代码解析依据与历史合约目录。 |
| Sessions | 实际合约、`session_id`、`trading_day`、带时区的起止时刻、`phase`、报单 / 撤单 / 撮合权限、权限受理层级、竞价类型及规则引用、订单延续规则、该交易日是否实际有夜盘；关联日历版本、常规模板、例外公告、来源及适用柜台能力版本。 |
| InstrumentStatus | 实际合约、原始状态、规范交易阶段、来源及接收时间、有效范围与质量标记；保留与日历冲突的证据，不能用过期状态放行请求。 |
| DominantMapping / ContinuousFactors | 决策与生效时间、输入版本、映射合约、调整参考价与因子、收益率视图的两端合约和时刻；用于信号的所有输入满足当时可见性。 |
| AccountSnapshot | 账户、查询批次、所属交易日、结算版本、事件游标、一致性状态及资金 / 持仓视图；原始半结算结果与最后一致快照分开保存，不混入行情 Parquet。 |

Sessions 从已选规则版本生成实际时段，起止区间按左闭右开解释，同一合约及时点的阶段与权限须唯一；正常休市显式表示，规则缺口或冲突标记为未知，不能静默补成连续交易。只撤不报窗口必须可独立表达。

原始 Tick 的累计成交量转换成增量时，处理交易日重置、重复快照、连接中断和缺失首笔，不能简单对所有负差值取零；来源的单边 / 双边口径、异常哨兵值、空盘口和时钟偏差需规范化并保留原始值（FR-DATA-09）。

### 7.5 SQLite 库职责、PRAGMA 与备份

来源：规划 §5.4；FR-DATA-07、NFR-04。

| 库 | 内容 |
| :--- | :--- |
| `meta/control.db` | 数据集 manifest、合约目录、交易日历、能力配置、历史规则来源和实验索引。 |
| `live/trading.db` | 控制者及控制代次、订单意图及发送状态、柜台标识、待关联 / 唯一成交、规范事件、账本、预占、风控计数、生命周期任务、查询批次、处理游标及账户快照。控制代次的恢复须满足不回退要求，不能仅用旧业务快照覆盖当前控制记录。 |

连接初始化至少包含以下设置，并按实际 SQLite 版本检查生效结果：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

`FULL` 用于保护已提交的订单及规则记录，但仍须在目标文件系统验证故障恢复。备份使用 SQLite 备份接口或一致性快照，不能在活跃 WAL 模式下仅复制主数据库文件；Checkpoint、保留策略及恢复演练纳入运维（`scripts/backup_state.py`）。每个库采用受控写入者和短事务；交易意图持久化失败时不得继续发送增加风险的订单。

### 7.6 历史规则表 DDL

来源：规划 §5.4.2；FR-RULE-01。核心字段示例；合约、来源、保证金、能力和舍入规则使用配套目录表维护，实现迁移时补齐外键及版本区间校验。

```sql
CREATE TABLE contracts_rules_history (
    rule_version_id TEXT PRIMARY KEY NOT NULL,
    instrument_id TEXT NOT NULL,
    account_profile_id TEXT NOT NULL,
    effective_from TEXT NOT NULL,
    effective_to TEXT,
    available_at TEXT NOT NULL,
    multiplier TEXT NOT NULL,
    price_tick TEXT NOT NULL,
    margin_rule_id TEXT NOT NULL,
    capability_profile_id TEXT NOT NULL,
    source_id TEXT NOT NULL,
    CHECK (effective_to IS NULL OR effective_to > effective_from)
);

CREATE TABLE commission_rules_history (
    fee_version_id TEXT PRIMARY KEY NOT NULL,
    instrument_id TEXT NOT NULL,
    account_profile_id TEXT NOT NULL,
    offset TEXT NOT NULL CHECK (offset IN ('OPEN', 'CLOSE_TODAY', 'CLOSE_YESTERDAY')),
    effective_from TEXT NOT NULL,
    effective_to TEXT,
    available_at TEXT NOT NULL,
    fee_per_lot TEXT NOT NULL,
    fee_rate TEXT NOT NULL,
    rounding_rule_id TEXT NOT NULL,
    source_id TEXT NOT NULL,
    CHECK (effective_to IS NULL OR effective_to > effective_from)
);
```

- 精确数值使用规范十进制字符串并由领域层以 `Decimal` 解析；UTC 时间字符串固定格式和精度。校验拒绝非法数值、缺失来源及无法唯一确定的适用规则。行情价格有效域按实际合约、价差或复权序列类型判定（FR-DATA-08），不能将实际合约的价格条件直接套到全部派生序列。
- 生效区间按 `[effective_from, effective_to)` 解释，支持日内调整；历史修订保留旧版本，并规定替代关系和查询优先级。
- 日历配套规则（交易时段、竞价制度、夜盘及节假日覆盖）关联公告档案；规则按交易日生效时保留原始生效交易日，生成 Sessions 时结合品种夜盘映射解析物理区间，不能按自然日 00:00 简单切换；冲突未解决时不发布可交易日历。
- 保证金配套规则描述按金额 / 按手、方向、投机 / 套保标志、组合分组及优惠资格；账户资金使用规则单独记录浮盈可计入比例、浮亏处理、汇总范围、冻结及费用口径。

## 8. 实验快照与可复现性

来源：规划 §5.5；FR-VAL-07、NFR-01。每次回测生成不可变 `run_manifest.json`，至少包括：

- 数据文件列表、内容哈希、Schema、质量报告、下载及清洗版本。
- 策略代码提交或源码归档哈希，包含未提交改动；Python、依赖锁文件、运行平台及涉及的接口库版本。
- 策略类别、信号频率与参数、初始资金 / 持仓、账户资金使用规则、交易配对及盈亏归因规则、交易日历、手续费和保证金版本。
- 执行策略、目标时段 / 时刻、信号可见与订单生效规则、错过目标开盘后的处置；执行价格的数据源、版本、分辨率、来源字段与时段映射、缺失价格处理规则。
- 合约代码解析与目录版本、主力映射、连续收益构造及复权因子、移仓触发规则与腿序、撮合规则、`limit_liquidity_scenario`、成交量参与率、延迟分布、风险阈值及全部降级假设。
- 交易阶段及操作权限版本、解析后的 Sessions 文件或内容哈希、常规模板与例外公告引用、生效基准及来源核验状态；重跑时不自动换成最新日历。
- 生命周期与维护配置、未决请求的查询 / 告警超时、回放模式与倍速、故障注入配置、启用的 A25 子场景和证据类型。
- 随机种子、同时间事件优先级、数据排序规则、时间范围、样本划分及输出哈希；清单不包含账户凭证。

不可变性与容差：

- 引用的原始及规范文件按内容或版本不可变发布。硬链接只用于受不可变管理的源文件，禁止原地写入；不满足条件时使用独立副本。目录只读标记本身不能保护共享文件内容。
- 同一环境、输入和随机种子下，重跑应得到相同订单、成交和账本结果；跨平台数值差异采用事先声明的容差并保留环境信息。
- 数据补录、规则修订、代码或配置变更应生成新的实验标识，不覆盖旧结果（A15）。

## 9. 回放与影子架构

来源：规划 §6.5、§6.6；FR-VAL-05、FR-VAL-06。

| 工具 | 输入 | 经过的组件 | 验收目的 |
| :--- | :--- | :--- | :--- |
| `scripts/replay_market_data.py` | 固定版本的历史 Bar / Tick | 行情端口 -> 虚拟时钟 -> 策略 -> 共享内核 -> 风控 -> `SimulatedGateway` -> 归一化 -> 订单管理 -> 账本 | 从行情输入实际产生策略意图、风控结果、模拟回报与账本；时序、订单及账本正确性（A28、A25） |
| `scripts/replay_events.py` | 已有交易事实（快照游标 + 规范事件） | Journal 重放 -> 共享内核 | 恢复正确性：订单、预占及账本差异（A04、A14） |

架构约束：

- 两者复用回测引擎和既有领域逻辑，不另建一套交易系统。
- 回放强制绑定 `SimulatedGateway` 和隔离的状态存储，不加载实盘凭证或向真实交易端口发送请求；所需规则、结算数据与初始持仓一起锁定版本。
- 支持单步、原速、加速及尽快运行；日历、延迟、查询超时与定时任务均由虚拟时钟推进；无新行情时仍推进结算、定时器和恢复任务。
- 可注入集合竞价边界、日盘再竞价 / 只撤窗口、夜盘残留单、历史规则切换、节假日停复市、休市、缺失行情、乱序回报、部分成交、断线与半结算查询。
- 首次对照由独立手工样例确定，不能只检查两次运行彼此一致。
- 首版先交付 Bar 路径，Tick 路径随类别扩展；回放标记为离线验证，不代替目标柜台联调、实时运行时长或真实滑点证据。

影子架构（`engine/shadow_engine.py`）：接入真实 CTP 行情，策略与共享内核正常运行，执行端口接模拟撮合；记录每个订单意图的假设成交价、数量与时刻。小额并行时，同一订单意图分别进入模拟撮合与唯一真实执行服务，按实际合约、方向、触发时点及手数关联比较；数量不同的结果单独列示。`shadow_report.py` 按周输出实际对假设的滑点、成交率、耗时及样本数，区分实时观测、历史回放和故障注入证据。

## 11. 精度与性能约束

来源：规划 §3.4 回测模式的端口适配、§4.4.1；FR-LED-04、NFR-02。

- 满足报价步长的委托 / 成交价格可用整数 Tick 表达；报单价格比较优先转换为整数 Tick。
- 结算价、平均价及复权指标保留各自所需精度，不强制取整到报价 Tick。
- 费用与盈亏用足够精度的定点数计算，在规定的记账环节舍入到最小货币单位，避免逐项提前取整；规则解析可使用 `Decimal`。
- 与柜台比较时明确最小金额单位和允许误差。
- 热路径优化须通过 A06、A07、A15 验证；性能优化不得改变舍入、事件顺序或交易语义。
- 容量预算以代表性订阅合约数和报单负载实测资源、吞吐、尾部延迟和恢复耗时为依据，记录测试硬件及数据规模（FR-OPS-05）。

## 12. 架构决策记录（ADR）

### 12.1 已决定项（来源：规划）

| 编号 | 决策 | 背景 | 后果 |
| :--- | :--- | :--- | :--- |
| ADR-01 | 回测与实盘共享一套领域内核，通过 Port/Adapter 切换 | 分别维护两套资金 / 持仓算法会导致回测与实盘语义漂移（规划 §3.4） | 领域层不得依赖任何适配器；所有模式差异只能出现在适配器与装配入口。 |
| ADR-02 | 独立执行服务作为唯一交易出口，单实例，持久化 `controller_id` / `control_epoch` | 进程内止损随进程退出失效；多个入口并发发单无法保证控制权（规划 §4.5.5） | 策略、看门狗、人工命令都不直接登录交易接口；接管需先隔离旧出口并对账。 |
| ADR-03 | 单一账户执行序列串行更新状态，回调只入队 | 多回调线程直接修改状态会破坏冻结不变量与去重（规划 §3.4） | 需要一个明确的入队机制（见 ADR-X2）。 |
| ADR-04 | 交易事件与元数据用 SQLite（WAL + FULL），本地磁盘，不用网络共享文件 | 首版单账户、单机；需要事务、游标与一致性备份（规划 §5.4） | 不用网络共享文件承担多进程交易协调；本地受控写入与 IPC 方案另按 ADR-X1 核验，备份用 SQLite 备份接口。 |
| ADR-05 | 行情录制采用短周期完整文件 + manifest 原子发布，而非追加日志 | Arrow IPC 不承担 WAL 承诺；首版低频不需要亚秒 RPO（规划 §5.1） | RPO 由实测水位定义；更低 RPO 时再引入带校验和的追加日志。 |
| ADR-06 | DuckDB 只读分析已发布 Parquet，不承担交易事务 | 避免研究查询争用实盘资源与混读多版本（规划 §5.3） | 查询必须从 manifest 取文件列表；设置资源预算。 |
| ADR-07 | 回测事件库使用内存适配器，运行结束导出规范事件 | 回测交易事件不要求 SQLite 耐久性，且需要高吞吐（规划 §3.4） | 回测快照通过导出事件对账；SQLite 交易事件日志用于模拟盘与实盘，元数据/规则库不受此限制。 |
| ADR-08 | 主力识别（数据层）与账户移仓（交易层）解耦 | 映射变化不应自动修改仓位（规划 §4.3.3） | `RollManager` 只通过 MappingStorePort 消费已发布版本。 |
| ADR-09 | 精度：整数 Tick 表达委托价，Decimal / 定点数计算费用与盈亏，在记账环节舍入 | 逐项提前取整导致与结算单不一致（规划 §3.4、§4.4.1） | 热路径优化受 A06、A07、A15 约束。 |
| ADR-10 | 向量化研究通道与事件驱动内核并存，共用数据映射、执行时点、价格来源与成本口径 | 参数扫描需要快速通道；正式评估需要成交、资金、风控（规划 §3.3） | 两条通道的一致性验证方式见 ADR-X4。 |

### 12.2 【评审补充】待决项（状态：待确认）

以下项目在规划中未指定，来自上一轮评估。此处只列候选与取舍，不作决定；决定后转入 12.1 并在 06 开发计划中安排验证。

#### ADR-X1 进程模型与 IPC 【评审补充】 状态：待确认

- 问题：策略进程、独立执行服务、看门狗、人工控制之间如何传递意图、事件、心跳与控制命令；`control_epoch` 如何随消息传递并在接收端校验。
- 候选：
  1. 命名管道（Windows Named Pipe）+ 长度前缀消息：无外部依赖，Windows 原生；需自行处理重连、序列化与多客户端。
  2. ZMQ（REQ/REP + PUB/SUB）：成熟的消息语义、跨语言；引入原生依赖，需处理消息丢失与队列高水位。
  3. SQLite 轮询（命令表 + 事件表）：与 `live/trading.db` 同一事务模型，天然持久化与审计；延迟取决于轮询周期，多进程写入需注意锁竞争，且规划要求"不用网络共享文件承担多进程协调"仅针对网络文件系统，本地文件需单独评估。
- 取舍要点：控制命令必须可审计并携带代次（倾向持久化路径）；订单事件需低延迟（倾向管道 / ZMQ）；首版低频 CTA 对延迟不敏感。
- 需要的验证：命令丢失 / 重复 / 乱序时的代次校验；进程崩溃后消息恢复；A23 接管序列。

#### ADR-X2 CTP 回调线程汇入执行序列 【评审补充】 状态：待确认

- 问题：CTP 封装的回调运行在 C++ 线程上；如何把回调事件安全交给单一账户执行序列，同时保证行情队列不阻塞交易队列。
- 候选：
  1. 专用执行线程 + 线程安全队列：回调线程只做转换与 `put`，执行线程串行消费；行情队列与交易队列分开；简单、易推理。
  2. asyncio 事件循环 + `call_soon_threadsafe`：与定时器、IPC 统一在一个循环里；需确认所选 CTP 封装与 GIL 释放行为，避免回调阻塞。
- 取舍要点：两者都满足"回调只入队"；差异在定时事件、IPC 和回测虚拟时钟能否共用同一调度抽象。
- 需要的验证：回调期间抛异常不丢事件；队列满时的故障策略；A02 乱序 / 重复回报在该模型下的去重。

#### ADR-X3 本机时钟同步与偏差监控 【评审补充】 状态：待确认

- 问题：规划 §6.3 用毫秒延迟建模，A25-04 区分 08:59:00 与 08:59:01 到达，但未定义本机时钟与交易所 / 柜台时间的对齐方式。
- 候选：
  1. 操作系统 NTP 或等效同步 + 开盘前同步状态检查；记录同步服务提供的可信偏差指标，使用单调时钟测量耗时。事件时间与本地接收时间差作为另一个传输/处理时延指标，不等同纯时钟偏差。
  2. 不做主动同步，仅记录偏差并在超阈值时进入保守门禁。
- 取舍要点：实盘时段边界仍由日历与状态回报共同判断；墙钟偏差影响边界与事件关联，单调时钟用于耗时和超时，二者不能混用。具体同步方案、阈值及证据质量规则属于 PROP-07 待确认范围。
- 需要的验证：同步与偏差指标进入 08 §4.1，开盘检查记录其状态；回放使用受控虚拟时钟，不把合成的零偏差当成实盘同步证据。

#### ADR-X4 向量化与事件驱动的分层一致性 【评审补充】 状态：待确认

- 议题：PROP-05。两条通道共享映射、执行时点、价格来源和成本口径；成交量预算、部分成交、资金或硬约束拒单等模型差异可能使权益结果不同。
- 建议分层验证：先对齐相同策略的信号与共同输入；在成交与风控假设相同的固定样例上比较规范结果及事先声明容差；在不同假设的样例上解释差异来源和适用范围。
- 不用宽容差掩盖输入错位，也不要求不同成交假设下权益曲线机械接近。
- 需要的验证：固定样例的共同输入对照、规范结果和差异归因；状态仍待确认，未形成新的正式验收门槛。

#### ADR-X5 组合层仓位分配归属 【评审补充】 状态：待确认

- 问题：多品种 CTA 的波动率目标、品种权重、保证金占用率上限等组合级仓位决定在哪一层实现；规划只有"保证金占用率上限作为内部风控规则"和"多策略按账户净额路由"。
- 候选：
  1. 放在策略层：策略自身输出经组合缩放后的 `target_position(product)`；内核只做路由与风控。
  2. 在共享内核增加组合分配组件：接收多个策略的原始目标，按配置分配后再路由；分配规则进入运行清单与快照。
  3. 放在 `research/` 作为离线参数：组合权重作为策略参数输入，运行期不动态调整。
- 取舍要点：候选 1 最简单但多策略共用账户时权重冲突无处协调；候选 2 增加内核职责与验收面；候选 3 适合首版低频，但无法响应盘中保证金变化。
- 需要的验证：多策略同品种反向意图（规划 §3.4）在所选方案下的归属与净额路由；A08 并发开仓与占款。
